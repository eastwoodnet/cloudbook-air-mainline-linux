## 首版测试流程（历史）

真机测试前必须重新把 A 槽设为三次试启动，不能沿用当前 permanent A 状态直接测试未验证内核。新增 `flash_612_candidate_from_linux.sh`，用于从当前 USB Linux 执行以下流程：

1. 核对设备、Rootfs、桌面服务、候选哈希和已知良好的 4.19 备份。
2. 备份当前 misc，只修改 AvbABData，保留其他启动元数据。
3. 经交互确认后仅写 `boot_a` 和 `misc`，读回校验，不自动重启。
4. 另行确认重启后，以 UART 检查内核、ROOTFS 和 Armbian 控制台。

## v1 真机结果与 v2 修正（2026-11-12）

v1（SDIO 启用）已由 UART 证实能够进入 6.12 内核：CPU、TTY、eMMC、USB/xHCI/EHCI、I2C 和 RTC 均有初始化日志。启动停止在：

```text
dwmmc_rockchip fe2c0000.mmc: allocated mmc-pwrseq
mmc_host mmc1: card is non-removable.
```

此位置对应 MT7663S 所在的 SDIO Wi-Fi 主机，尚未执行最小 initramfs。因此当前证据指向 SDIO 首启阻塞，不能据此判断 USB Rootfs 或整个 6.12 内核不可用。

v2 仅将 `&sdmmc1` 改为 `status = "disabled"`，暂不按首启目标启用 Wi-Fi。内核 Image 保持原哈希，DTB 和打包镜像更新：

```text

SHA-256：e475ab7eb10231c6cb6053417cf41a0308788c8b55516ebb292dc69ce1e625f0
```

v1 镜像和 UART 证据已分别保存为 `build/boot_linux_612_minimal_v1_sdio.img` 与 `logs/uart-612-v1-mmc1-hang-20261112.txt`。v2 仍需单独确认后刷写和重启验证。

## v2 结果与 v3 诊断候选（2026-11-12）

v2 禁用 SDIO 后已越过 `mmc1`，说明 v1 的 SDIO 节点确实是首个阻塞点。v2 随后停在：

## v3 initcall 定位与 v4 候选（2026-11-12）

v3 的 initcall 日志显示 `devfreq_init` 已返回 0，下一条应为 `devfreq_event_init`，但没有出现其 `calling` 或 `returned` 记录。System.map 的 initcall 顺序已核对为：

```text
devfreq_init
devfreq_event_init
devfreq_simple_ondemand_init
```

v4 保留 v3 诊断参数，增加 `initcall_blacklist=devfreq_event_init` 和 `cpuidle.off=1`。前者跳过一个非首启必需的 devfreq-event class 初始化；后者用于排除多次启动停止位置不一致所涉及的 CPU idle/时序因素。

```text
文件：build/boot_linux_612_minimal_v4_skip_devfreq_event.img
SHA-256：3ed43dea54f9d61d3fe84f201421237884af931e8c1134ae29cde825e84adac5
```

v4 刷写后实机在 `calling devfreq_init` 瞬间出现整机断电，外接设备断电，长按 15~20 秒电源键硬件复位后安全回退 Android 11（Slot B）。当时判断为 PMIC（RK809/SC2021）硬件欠压死锁保护（PMIC Latch），但该因果后来被 v7 推翻。

## v4 后分析、v5 G3 极简构建与部署（2026-11-12）

通过 `06-4.19与6.12内核差异及外设映射分析.md` 的系统性对账，当时推断（后由 v7 推翻）：
1. 4.19 原厂 CPU `/cpus/cpu@0` 无 `cpu-supply`，固定 1.0V 不调压；
2. 6.12 DTS 声明了 `cpu-supply = <&vdd_cpu>` 与 `cpu0_opp_table`，当时怀疑启动时 `devfreq`/`cpufreq` 调压瞬间欠压导致 PMIC Latch（**未证实**）；
3. 6.12 DTS 提前开启了 33 个节点，但对应 DRM、Audio、GPU 驱动全为模块（`=m`），可能在 4.2s `clk: Disabling unused clocks` 时关闭总线时钟导致停滞（**机制未完全证实**）。

v5 严格遵循 `rk-linux-bringup-skill` 的 P3 G3 规范生成极简设备树（`rk3568-ecloudbook-air-24rtw-v5-g3-clean.dts`）：
- 拔除 CPU `cpu-supply` 调压，`vdd_cpu` 锁定固定 1.000V；
- 设计上要求禁用硬件看门狗 `&wdt`；**但实际 v5 DTS 与 v8 DTB 中 `&wdt` 仍为 `status = "okay"`，该条未落实，需后续修正**；
- 禁用 GPU、VOP2、HDMI、Audio（I2S0/I2S1/PDM/Codec）、SDIO Wi-Fi、SARADC 等全部非核心节点；
- 仅保留核心 5 项：调试串口 `uart2`、PMIC 与固定电源 `i2c0`、存储 `sdhci` (eMMC)、USB Host 控制器与 PHYs；
- 启动参数配置：`console=ttyS2,115200n8 earlycon=uart8250,mmio32,0xfe660000 root=LABEL=ROOTFS rootfstype=ext4 rootwait rw clk_ignore_unused pd_ignore_unused cpuidle.off=1 initcall_debug`。

产物：
- 镜像：`build/boot_linux_612_minimal_v5_g3_clean.img`
- 大小：`82,178,048 bytes` (78.37 MiB)
- SHA-256：`451b386e4944fc5752d292c5009617e86c7ee6cf039a5309b4b46b44aaa1844c`

部署与回读验证：
- 已通过 ADB (`<DEVICE_IP>:5555`) 刷入 `boot_a`；
- 已写入 `misc_try_slot_a.img`（Slot A 设为 3 次试启动，失败自动回滚 Android B）；
- 实机回读校验：
  - `boot_a` 前 82178048 字节 SHA-256 读回比对完全一致 (`451b386e4944fc5752d292c5009617e86c7ee6cf039a5309b4b46b44aaa1844c`)；
  - `misc` 4194304 字节 SHA-256 读回比对完全一致 (`6926242261e443a0993b6d01efa85419145ab0c1e70401d6acec60076e96f04b`)；
- **设备未执行重启**，等待用户现场操作确认。

## v6~v8 真机结果与最终点亮（2026-11-12）

> **重要修正**：v7 去掉 CPU `cpu-supply` 后仍在约 4.2 秒复位，因此上一节“PMIC 欠压是 v4 根因”的结论不能作为已证实结论保留。v8 DTB 中 `&wdt` 仍为 `okay`，但运行态 `dw_wdt_early` 读到 `cr=0x00000008`（使能位 0），随后 `dw_wdt` probe 注册 `timeout=44`；这说明 U-Boot 遗留 DW watchdog 也不能单独解释全部复位。完整复位机制仍需后续对照实验确认。

v6 增加了可交互救援 initramfs；v7 重新整理启动链和救援流程。v8 在 6.12 `dw_wdt.c` 中加入早期寄存器诊断与按需喂狗代码，并复用 v7 救援 initramfs。v8 是首个实际进入用户态的镜像：
