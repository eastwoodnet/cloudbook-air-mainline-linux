## 目标与当前状态

目标设备为中兴 eCloudBook Air 24RTW（RK3568、W620D V12）。上一轮将实验 boot 镜像写入 `boot_a` 后启动失败，设备随后回到 `boot_b` 的 Android 11。

2026-11-10 已通过指定 ADB 设备 `<DEVICE_IP>:5555` 只读确认：当前槽位为 `_b`，`bootctl get-current-slot` 返回 `1`，Verified Boot 状态为 `orange`，adbd 已具有 root 权限。未对设备执行分区写入或重启。

本轮目标是先得到可复现、可诊断的内核与最小 Linux 系统，再逐项恢复外设。任何候选镜像在完成本地验证、UART 准备和单独刷写确认前，都不得写入设备。

## 关键技术决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| eDP 修复层级 | 修改并重建完整内核，同时修正 DTS | 当前预编译内核缺少 RK3568 eDP 控制器匹配和 PHY 实现，仅修改 DTS 无法解决 |
| 面板实现 | 在 `panel-simple` 增加 BOE NV140WUM-N44 描述，DTS 使用专用 compatible | 当前 `boe,nv140wum-n44` 与通用 `simple-panel` 均无匹配项 |
| 临时显示 | `simple-framebuffer` 只用于诊断，不作为最终显示方案 | 不能替代 DRM、eDP 供电和 link training |
| 内核来源 | 扩展现有 `unifreq/linux-6.18.y` 源码树并保存独立补丁 | 便于复现、审查和后续重基，不再把 ophub 预编译内核当作定制构建结果 |
| 首个 Rootfs | 可擦写 USB 盘上的最小 ARM64 Debian/Armbian 系统 | 不改内置 eMMC 分区，便于在电脑上修复系统文件 |
| Rootfs 卷标 | 统一使用 `ROOTFS` | 与当前打包脚本及 boot 镜像 cmdline 一致，消除文档中的 `armbian_root` 分歧 |
| initramfs | 最终使用与自构建内核、Rootfs 匹配的 initramfs | 避免继续使用仅适配 `6.18.62-ophub` 模块的旧 initrd |
| 首次部署 | 仅写 `boot_a`，保留当前可用的 `boot_b` | 保留 Android 恢复路径 |
| 首次启动观测 | UART2 串口日志为主，ADB/SSH 为辅助 | 显示、Rootfs 或网络失败时仍能定位内核阶段 |

## eDP 与面板实施拆分

1. 从 Rockchip BSP 或已有补丁中寻找 RK3568 Analogix eDP 控制器和 `fdcb0000` PHY 的可移植实现；现有反编译文件用于核对寄存器、时钟、复位和 V12/V13 摆幅/预加重逻辑。
2. 在 6.18 内核中实现或移植控制器匹配数据与 PHY 驱动，不仅添加 compatible 字符串。
3. 为 BOE NV140WUM-N44 添加面板时序和上下电延迟，移除无效的通用 `simple-panel` 回退假设。
4. 保持 eDP 接 VOP2 VP1，并检查端口、时钟、复位、电源域和面板供电依赖。
5. 保留 `-@` 生成的 `__symbols__`，验证 `chosen`、`reboot_mode` 和新增节点均可被 overlay 定位。
6. 先执行编译、`dtbs_check`/DTB 结构检查和镜像内容检查；没有 UART 前不进行真机显示测试。

## Rootfs 实施拆分

工作区目前只有 kernel、initrd、模块压缩包和固件，没有完整 Rootfs，因此必须新准备。

首版 Rootfs 仅包含：

- ARM64 最小 Debian 或 Armbian 用户空间；
- 匹配自构建内核版本的 `/lib/modules`；
- MT7663 固件及后续验证所需固件；
- 串口控制台、基础网络、SSH 和调试工具；
- 根分区卷标 `ROOTFS`。

当前 USB 网卡为 `0fe6:9900`。现有内核配置及上游 USB 网卡驱动中未发现明确的 SR9900 支持，不能假定它在自构建 Linux 中可直接使用。调试网络可改用已知受主线支持的 AX88179/RTL8153 USB 网卡，或者后续单独适配现有网卡。Wi-Fi 也需在对应模块和固件部署后验证。

桌面环境、内置 eMMC Rootfs 和 Android 双系统日常使用优化均放在最小系统启动之后。

## 分阶段实施计划

### 阶段 0：保存现场与建立基线

- 使用明确指定的 ADB 序列号，不再依赖其他历史地址。
- 读取并备份当前完整 `boot_a`、`misc` 和槽位状态，生成 SHA-256 清单。
- 保留失败镜像和原厂 `boot_b`，不覆盖历史证据。

### 阶段 1：可复现构建

- 完善 DTS 预处理、`dtc -@`、resource 容量和镜像大小检查。
- 扩展完整内核源码，准备 AArch64 交叉编译环境。
- 保存内核配置和独立补丁，记录构建命令及产物哈希。

阶段 1 的 DTB/打包器修复已完成，但包含定制内核的最终构建尚未完成。

### 阶段 2：eDP、面板及已知 DTS 冲突

- 完成控制器、PHY、面板移植。
- 修复 DMIC GPIO 重复占用等已确认问题。
- 输出自构建 kernel、DTB、模块和静态验证记录。

### 阶段 3：最小 USB Rootfs

- 制作 `ROOTFS` 卷标的最小 ARM64 系统。
- 安装匹配模块、固件和 initramfs。
- 在电脑上检查卷标、init、模块依赖、固件路径和文件系统完整性。

### 阶段 4：刷写工具与启动验证

- 刷写工具必须检查目标序列号、产品型号、当前 B 槽、分区容量和本地镜像哈希。
- 写前备份，写后按实际长度做 SHA-256 读回；校验失败时禁止自动重启。
- 明确配置 Slot A 的试启动次数，不以 `bootctl set-active-boot-slot 0` 替代回退策略检查。
- 接 UART 后，经用户单独确认才写入 `boot_a` 并重启。
- 保存完整串口日志，按启动阶段处理失败，不连续盲刷。

### 阶段 5：外设与电源链验收

按显示、USB 键盘、触控板、eMMC、Wi-Fi/蓝牙、音频、电池、BQ25700、SC2021 PD、suspend/resume 的顺序逐项验证。当前预编译配置未启用 SBS/BQ257xx，SC2021 也只有驱动草案，这些必须在自构建内核中单独完成和测试。

## 需要准备的物品与环境

### 用户需要准备

1. 一个可完全擦写的 USB 盘或 USB SSD，建议至少 16 GiB，其中不得保留重要数据。
2. 可接触主板 UART2 焊盘的 USB 转串口工具，支持 1500000 baud；接线前确认接口电平，只接 TX/RX/GND，不接 VCC，禁止直接接 RS-232 或 5V UART。
3. 稳定供电和可正常使用的 Android `boot_b`。
4. 建议准备恢复用双公头 USB-A 线，但在核实接口和流程前不连接、不执行刷写。
5. 可选：已知受主线支持的 AX88179 或 RTL8153 USB 网卡，用于避免当前 `0fe6:9900` 网卡影响调试。

### 主机环境

当前主机约有 532 GiB 可用磁盘、4 个 CPU 和 8 GiB 内存，足够进行内核构建。需要补齐 AArch64 交叉编译器及内核构建软件包；安装系统软件前另行说明并确认。

## 完成标准与风险边界

首个里程碑不是“生成 boot.img”，而是“UART 证明自构建内核启动、挂载 USB Rootfs 并进入控制台”。显示和每个外设分别记录为未实现、已编译、已 probe、已真机验证，禁止用原厂 Android 的工作状态替代主线验证。

A/B 回退已观察到设备回到 Android B，但不能据此宣称零风险。不得修改 idbloader、U-Boot、Trust、当前可用的 `boot_b` 或内置 Rootfs 分区，除非后续有单独的必要性说明和明确确认。
