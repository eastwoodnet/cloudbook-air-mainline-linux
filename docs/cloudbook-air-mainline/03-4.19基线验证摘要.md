## 结论

ZTE CloudBook Air CT2000-24RTW（RK3568、W620D V12）已形成一个可用的 Linux 验证基线：**原厂 4.19.193 内核 + 原厂 V12 DTB + 自定义最小 initramfs + USB Armbian Rootfs**。

截至 2026-11-11，以下项目均已由用户在实际设备上确认可用：

- 内置 eDP 屏幕显示，原生模式 `1920×1200@60Hz`；
- 内置键盘输入；
- 内置触控板移动和点击；
- RK809 声卡经内置扬声器播放测试音。

当前系统通过 Xorg 的 modesetting 驱动使用 DRM/KMS，运行 openbox 和 xterm。显示问题已经解决，不再需要围绕 fbdev、虚拟控制台或短时 `modetest` 继续盲试。

## 2. 显示问题定位与有效方案

### 2.1 已排除的方向

启动初期屏幕保留 logo，直接写 `/dev/fb0`、运行 `fbterm` 和短时 `modetest` 均未得到可用桌面。这些现象不能证明面板、eDP 主链路或 VOP 硬件损坏。

运行时曾确认：

- `card0-eDP-1 = connected`；
- 面板 EDID 为 BOE `NV140WUM-N44`；
- 原生时序为 `1920×1200@60Hz`；
- `link-status = Good`、`DPMS = On`；
- VOP/eDP 时钟和 `pd_vo` 电源域正常；
- eDP 使用 `video_port1`，即 VOP2 VP1。

原厂内核配置存在关键限制：

```text
# CONFIG_VT is not set
CONFIG_DRM_KMS_HELPER=y
CONFIG_DRM_FBDEV_EMULATION=y
```

因此系统没有正常可用的虚拟控制台，`chvt`、`/dev/tty1` 和依赖 VT 的终端方案不能作为屏幕登录路径。手工创建 `/dev/tty1` 设备节点不会增加内核 VT 支持。

### 2.2 最终验证通过的显示栈

使用以下用户态组件：

- `xserver-xorg-core`，使用其中内置的 modesetting 驱动；
- `xinit`；
- `openbox`；
- `xterm`；
- `xserver-xorg-input-libinput`；
- `x11-utils` 和 `x11-xserver-utils`。

Xorg 日志确认：

- modesetting 驱动成功打开 `/dev/dri/card0`；
- 正确读取 eDP EDID；
- 选择 `1920×1200@60Hz`；
- libinput 成功接管内置键盘和触控板；
- Xorg、openbox 和 xterm 持续运行。

最终内屏状态：

```text
Screen 0: current 1920 x 1200
eDP-1 connected primary 1920x1200+0+0
1920x1200 60.00*+
```

终端窗口位于内屏，实测几何信息为 `1915×1174+1+20`，窗口装饰之外基本占满屏幕。

### 2.3 当前启动方式

本地持久化配置：`rootfs_build/overlay/root/.xinitrc`。

设备路径：`/root/.xinitrc`。

当前内容：

```sh
#!/bin/sh
# 原厂 4.19 内核未启用 VT；Xorg 由启动命令使用 -novtswitch -sharevts。
# 当前只使用内屏，避免 openbox 把最大化窗口放到外接 HDMI 桌面。
xrandr --output HDMI-1 --off --output eDP-1 --mode 1920x1200 --primary
openbox &
exec xterm -maximized -fa Monospace -fs 16
```

手动启动命令：

```bash
xinit /root/.xinitrc -- /usr/lib/xorg/Xorg :0 \
  -novtswitch -sharevts -logfile /var/log/Xorg.0.log
```

`-novtswitch -sharevts` 用于适配当前无 VT 的原厂内核。`xrandr` 命令关闭 HDMI 扩展桌面，避免最大化窗口被 openbox 放到 HDMI 一侧。

**当前尚未配置 systemd 自动启动桌面。** 已安装的软件包和 `/root/.xinitrc` 会保留在 USB Rootfs 中，但重启后需要手动执行启动命令，或者后续增加专用服务。

### 2.4 非阻塞日志

Xorg 中存在 `systemd-logind: failed to take device ... Operation not permitted` 和 openbox 缺少 Debian 菜单文件的提示。当前 root 会话已取得 DRM 和输入设备，以上提示没有阻止本次显示、键盘和触控板验证，暂不作为优先问题处理。

短时 `modetest` 未出画面的具体用户态原因未继续追查；持续运行的 Xorg 已证明实际显示链路可用，因此不再将该现象作为内核阻塞项。

## 5. 安全边界与后续工作

当前安全约束保持不变：

1. 任何后续刷写前必须单独告知并等待确认。
2. 只允许写实验用 `boot_a` 和回退所需的 `misc`，保留可用 Android `boot_b`。
3. 不刷写 idbloader、U-Boot 或 Trust，不自动重启。
4. 看门狗不是可靠回退机制，继续使用三次试启动回退。
5. 操作 USB U 盘前必须重新核对 `/dev/sdX`，防止误擦主机系统盘。
6. 源码改动保持未提交、未推送；当前工作区根目录不是 Git 仓库。

建议下一步按以下顺序进行：

1. 为已验证的 Xorg 桌面增加专用 systemd 服务，并验证重启后的显示、键盘、触控板和声音是否仍可复现；执行重启前另行说明。
2. 保存当前 USB Rootfs 的软件包清单和必要配置，形成可恢复基线。
3. 再验证摄像头、电源管理、HDMI 和 suspend/resume，Wi-Fi 继续暂缓。
4. 在 4.19 基线稳定后，基于 Armbian Rock-3a 用户空间评估 unifreq `6.12 LTS`，不再继续无证据地参数化盲试 6.18。

参考资料 `https://github.com/ophub/amlogic-s9xxx-armbian/issues/3762` 表明其他 RK3568 设备可通过主线内核和 Armbian 实现 HDMI 显示，但不能直接替代本机 V12 的 eDP、电源和外设适配证据。

## 6. 当前里程碑判断

“原厂 4.19 基线可启动”已升级为“**具备本地图形终端和核心人机交互能力的 4.19 验证系统**”。

这还不是完整的主线移植完成状态：当前内核和 DTB 来自原厂，桌面尚未自动启动，若要进行主线化仍需在 6.12 LTS 上重新验证启动、eDP、输入设备、声卡和电源链路。
